# Milestone 3.7 — traversal hitch diagnosis

## Result

**Confirmed trigger: changing the number of visible PointLights as the camera moves, causing new Three.js WebGL shader-program variants to be linked during `renderer.render`.** This is a render/driver stall, not a facility/terrain reconstruction on crossing a chunk boundary. Milestone 3.6 changed `updateBudgetLights()` from always-visible budgeted lights to distance-based `light.visible` switching every 0.25 s. The exact boundary for each light is a sphere around its world position of radius `max(55, light.distance + 35)` metres, tested against the camera position. There is no single fixed x/y chunk boundary: crossing any of these overlapping spheres changes the active light count. Three.js includes that count in material program variants; the cached world geometry is stable, but the rendered shader configuration is not. Returning along the same route can encounter further light-count combinations. The earlier mission-transition improvement moved the cost out of the first full-world render by reducing initially active lighting, but deferred new lighting-program combinations into ordinary traversal.

The comparison below used the actual single-file game with `?perfDiagnostics=1`. The automated route moved the existing debug player 14 m per animation frame along waypoints (without clicking objectives), once forward and backward for each leg. It is **not** a real walking-speed or hardware FPS benchmark. Both headless browser environments used software WebGL; multi-second values should **not** be interpreted as expected desktop Firefox pause lengths. They do establish where time was spent and the causal effect of changing light visibility. No gameplay code was changed for the experimental ablation; it froze PointLight visibility in one browser page after the baseline lap.

| Two-lap M2 staging → Alpha → Beta → staging control | Firefox headless | Chromium headless |
|---|---:|---:|
| Baseline, 104 frames: p95 interval | 4768.8 ms | 5651.3 ms |
| Baseline, intervals >100 ms / long renderer calls | 9 / 9 | 15 / 14 |
| Baseline, new WebGL program links | 60 | 70 |
| **Same route with PointLight visibility held fixed**, 104 frames: p95 interval | **33.3 ms** | **17.1 ms** |
| Fixed lights, intervals >100 ms / long renderer calls | **0 / 0** | **1 / 1** |
| Fixed lights, new WebGL program links | **2** | **3** |

The remaining Chromium control stall linked three programs, so other first-use material variants can still contribute; the dominant recurring traversal stall was removed by the *test-only* light-visibility control. Holding all lights fixed is **not** the proposed production fix.

## Spatial evidence

An independent A–E forward/reverse pass in active campaign gameplay (no recording) covered: LZ `(450,80)` → facility staging `(360,580)`; front `(360,606)` → side `(405,643)` → rear `(425,705)`; rear/staging → Alpha `(205,575)` → Beta `(245,748)`; Beta via west/east bypass → Gamma `(575,585)`; Gamma → facility. The profiler was reset after world creation. In headless Firefox, 327 sampled intervals yielded p95 1350.3 ms, p99 6934.9 ms, worst 8735.4 ms, 27 intervals >50 ms and 23 >100 ms; 178 program links were counted. In headless Chromium, 327 intervals yielded p95 200.1 ms, p99 6168.1 ms, worst 7868.4 ms, 24 intervals >50 ms and 24 >100 ms; 116 program links were counted. Values reflect software rendering and the scripted traversal speed.

Example Firefox crossings: near `(448,132)` five lights changed; 10 programs linked, `renderer.render` took 8713 ms; near `(366,570)` 28 lights changed, 10 programs linked, render 6289 ms; near `(323,583)` 13 lights changed, six programs linked, render 6736 ms; near `(205,575)` 25 lights changed, six programs linked, render 5969 ms. `gameUpdate` was ~1–4 ms for those frames. Similar events recurred on the return path and around Beta/Gamma. Program count rose from 22 to 198 in the Chromium A–E pass, despite zero world-builder calls in the sampled movement intervals.

**Not implicated by these quiet traversal passes:** no `buildCampaignWorld`, `buildTerrain`, `buildFacility`, `buildDecor`, or environment-layer rebuild during traversal. No geometry/material creation, scene addition, or dispose burst coincided with the quoted large frames. A single `collisionNavRebuild` and allocations occurred at the deliberate M1→M2 *test mission switch*, not the movement boundaries. `rebuildEnemyGrid` is called every gameplay tick; measured JS update time was small. Minimap drawing and route-guide visibility are repeated work, but remained millisecond-scale and did not coincide with the large render stalls. `gameUpdatePost` gates the facility dust/material FX at a 190 m boundary and 12 Hz; no measured world reconstruction occurs there. Periodic 12 Hz shadow refresh is another render cost to watch, but the same-route light-visibility ablation isolates the main problem even with shadow refresh unchanged.

The GL `compileShader` and `linkProgram` calls themselves can report near-zero JS time because shader compilation and driver synchronization are deferred into the `renderer.render` call. This evidence identifies **shader-variant/render-path work** and its visibility trigger; it cannot apportion the blocking renderer time between JavaScript inside Three.js, synchronous WebGL driver work, and GPU completion without a browser GPU profiler. Headless browsers also showed some non-shader frame intervals >50 ms with no expensive game operation (possible scheduling/GC); they are separate from the repeatable light-boundary stalls.

## Phase 1 recommendation (implemented in the stabilization phase below)

Keep the same facility, route lights and gameplay, but avoid changing the **number of active Three.js PointLights** as the player crosses budget boundaries. Choose a stable per-render light configuration or a bounded fixed set of reusable light slots whose positions/intensities can change without changing shader defines. Verify in *desktop* Firefox that active program count stops growing during back-and-forth traversal, with no render-time spikes correlated to light changes. Do not simply turn off lights or drop visual quality. Review shadow refresh only if stalls persist after the primary correction.

## Instrumentation and manual Firefox check

Open `chargefront.html?perfDiagnostics=1` in Firefox (on `file://`, add the query string to the file URL). Without the query string the profiler is absent. The small HUD updates once per second. After landing and waiting for world setup, open Firefox DevTools Console and run `__cfPerf.reset()`. Walk from the landed LZ toward the facility and back; then, in Mission 2, move from staging via Alpha, Beta and the west/east bypass toward Gamma, reversing direction at least twice. Before stopping, run `__cfPerf.download()` to save JSON. `__cfPerf.mark('front gate')` adds a route marker; `__cfPerf.summary()` gives compact totals; `__cfPerf.report()` includes up to 3,600 recent frame samples and 2,000 hitch records. In a hitch record, compare `state.x/y/z`, `state.phase`, `events` (`budgetLights`, `shaderPrograms`, `facilityFxBoundary`), `delta.linkProgram`, `renderMs`, `ops`, `renderer.programs`, and allocation/disposal deltas. RAF frames >33, >50 and >100 ms are counted cumulatively; p95/p99 and average use the most recent 3,600 frames. If desktop Firefox exhibits a slow frame without light changes or new shader programs, retain that record as evidence for a secondary cause.

Instrumentation is isolated in `chargefront.html`: the query flag at the module start, boundary/light counters in `rebuildSolidGrid`, `updateBudgetLights`, `gameUpdate`, and `gameUpdatePost`, and the flagged profiler before `boot()`. It wraps world builders, collision/nav, mission and enemy systems, minimap/marker draws, `Object3D.add/remove`, geometry/material disposal, WebGL shader/link calls and `renderer.render`. Its geometry/material counters observe previously unseen resources when an object is added to a Three.js group (not every unreferenced constructor call); scene-add/remove counts only apply to already scene-attached parents. A feature-detected long-animation-frame observer is used where available, with RAF/performance.now as the Firefox-compatible fallback. There is no per-frame console logging.

## Stabilization implementation and validation

The authored terrain, facility, exterior, props, collision footprint and campaign state remain persistent. `addBudgetLight()` now keeps its authored PointLight as **mission/route-dependent source data**. During gameplay it is not submitted to the renderer. Eight permanently submitted `LocalLightSlot` PointLights instead copy the most influential eligible sources' world positions, colors, intensities, ranges and decay. The slots are created **once when a world is built**, not in the menu, and unused slots remain present at intensity zero. Changing source selection or a relay/lab/extraction state therefore changes light **uniforms**, not the PointLight count in Three.js shader defines. Source eligibility respects mission mode and every parent group's visibility; route/snapshot changes invalidate selection, and active source colors/intensities follow state changes between spatial selections. There is no light geometry, mesh or shader recreation caused by the traversal light selection. Facility reference captures keep their original full authored lighting outside gameplay.

The fixed slot count is deliberately small to avoid restoring a large first-render program. In a separate check of representative M2 camera positions, the top eight sources accounted for 97–100% of the sum of estimated local camera illumination (100% at side, rear, Alpha, Beta, Gamma and lab points; 97–98% at staging/front). This is a **selection heuristic**, not a measured promise of pixel-identical distant surfaces; the developer front/lab captures were checked against the saved references. The source light objects and their mission-specific properties are retained, not disposed or rebuilt.

World/terrain/facility builder calls during either A–E traversal pass: **zero**. Collision-grid rebuilds: **one at the deliberate M1→M2 test mission switch**, none at movement boundaries. Geometries/materials observed after reset in Firefox: **59/49 before and 42/38 after** (random mission-switch content, not the repeated hitches); Chromium **52/48 before and 42/38 after**. Scene-add counts across old/new files cannot be directly compared because the earlier diagnostic counted additions to detached groups and the current diagnostic counts only scene-attached parents; there was no traversal-time scene-add burst in either. At the end of the Firefox runs, `renderer.info` reported **200 → 23 programs**, 1126 → 1174 render calls, ~290k → ~292k triangles, 1483 → 1471 geometries and 14 → 14 textures. ### Desktop Firefox manual gate

1. Open `chargefront.html?perfDiagnostics=1`; launch a new campaign and let the landing/first render complete. In DevTools run `__cfPerf.reset()`.
2. Walk from the landed transport toward facility staging; circle the facility front, side and backyard, then reverse that short section several times.
3. In Mission 2 follow staging → Alpha → Beta → west/east facility bypass → Gamma, then return over the same path several times.
4. Check that the HUD's program count (or `__cfPerf.report().frames.at(-1).renderer.programs`) stabilizes rather than growing at each light boundary. Run `__cfPerf.download()` before closing the tab. Examine any >100 ms interval's `renderMs`, `delta.linkProgram`, `events`, `ops`, world/mission state and coordinates.
5. Verify the facility/lab lights, relay and purge-node states, ship continuity, minimap routes and normal combat visually. Remove the query string to disable all diagnostic hooks.

**Checkpoint:** the deterministic traversal-triggered shader-variant regression is resolved in both automated browsers, and measured chapter transitions remain small. Keep facility modularization on hold until the real desktop Firefox pass confirms acceptable ordinary frame cadence and initial render/lighting; if it does, make this runtime stabilization its own checkpoint commit before any facility redesign.
